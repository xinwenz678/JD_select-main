## 2. 必须确认的契约

| 项目 | 当前 A 的行为 | 需要团队确认的事项 |
|---|---|---|
| 新建匹配输入 | 计划为 resume_text、jd_text、job_title | 简历解析后人工修改的字段如何传给 C？只传原文可能丢失修正 |
| 评分值 | 整数 0–100，分项上限 60/20/20，分项和等于总分 | 若 C 使用小数，由谁舍入，是否先更新契约 |
| 解析结构 | resume_sections 是 JSON 对象 | 教育/项目/经历的键名与数组/对象结构 |
| 岗位技能 | job_skills 是 JSON 数组 | 必需/加分技能、证据位置、归一化名称的数据结构 |
| 建议 | suggestions 是 JSON 数组 | D 展示纯文本还是带类型/位置/建议的对象 |
| 保存事务 | create_record 只 flush，调用方 commit | 由 C 的编排统一提交，不重复保存 |
| 记录 ID | 服务端 UUID 字符串 | 前端以 id 打开详情，不用数组下标 |
| 历史列表 | items/total/limit/offset，默认最近 10 条 | D 分页控件及刷新逻辑 |
| 分析快照 | PATCH 只修改 job_title | 用户改简历后重新生成记录，不覆写旧评分 |
| 时间 | UTC 带时区 | D 按浏览器本地时区显示 |
| 算法版本 | 非空 algorithm_version | C 定义并随评分规则改动更新 |
| 错误 | error.code/message/details | D 不依赖 FastAPI 原生 detail 字段 |
| 长度 | 简历/JD 去首尾空白后最多 100000 字符 | B/D 校验与后端一致 |

特别待决策：用户在 B 的编辑界面修正解析结果后，C 必须使用同一份有效输入。当前计划请求仅含原文，尚未约定结构化修正的传递方式。方案应由 B/C/A 共同确认并同步 D，再更改生产契约。

## 3. 路由与代码归属

- A：core/database.py、core/errors.py、models/analysis_record.py、api/records.py、services/analysis_records.py。
- B：自有简历解析路由、服务及 schema，建议独立文件。
- C：自有 JD/匹配路由、算法服务及词典。
- D：页面、组件与前端请求适配。
- 共享入口 app/main.py、公共 schema 和依赖文件修改，由 A 汇总确认；这不是独占规则，目的是减少多人覆盖。

C 的 POST /api/matches 负责计算并调用 A 存储层。POST /api/analysis-records 仅保存已有计算结果，不能被当作真正的匹配接口。
所有路由挂载到同一个 create_app 应用，复用 get_session；不要各自启动独立 FastAPI 服务器或在模块导入时建库。

## 4. 分阶段联调顺序与判定

| 阶段 | 操作 | 通过条件 | 当前状态 |
|---|---|---|---|
| 0 | 每人记录分支/提交，执行 setup 和 verify | 可复现当前运行环境 | A 本地证据见验证记录；他人待确认 |
| 1 | D 调用 A 历史接口，用合成持久化样例 | 空态、列表、详情、错误显示正确 | 待 D 分支 |
| 2 | B 解析文本并让用户修正 | 字段和修正结果可追踪 | 待 B 分支和输入契约 |
| 3 | C 输出真实 MatchResult 并保存 | 分项一致，创建一次且能查询 | 待 C 分支 |
| 4 | D 调用 C 的 POST /api/matches | 显示真实评分，再打开历史详情 | 待 B/C/D |
| 5 | 全流程运行及错误场景 | 空输入、部分匹配等场景有明确实际结果 | 未执行 |

合成样例阶段只证明接口和页面能通信，不证明解析质量、评分正确性或完整 MVP 已完成。
算法效果验收数据应来自题目要求的 JD/简历分析，不能用固定分数证明算法正确。
