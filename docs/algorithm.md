## 0. 一句话总结（答辩用）

> 纯规则、无外部 API、同输入必同输出；总分 0-100 由 "必需技能 60 分 + 加分技能 20 分 + 经历证据质量 20 分" 构成，每个分数都能追溯到原文证据，技能未命中绝不猜测为已掌握。

## 1. 总体设计

### 1.1 核心链路



```
简历文本 ──┐

&#x20;          ├─→ C1 技能提取（词典+同义词+词边界）──→ 简历技能集合

JD 文本 ───┤                                          │

&#x20;          └─→ C2 JD 解析（切句+信号词分类）──→ 必需/加分/否定技能（带证据）

&#x20;                                                     │

&#x20;                                                     ▼

&#x20;                                       C3 评分：总分 + 分项 + 匹配/缺失 + 建议
```

### 1.2 四条设计原则



1. **纯规则、无外部依赖**：无 API Key 也能完整运行核心匹配（AI 仅用于 P1 的 STAR 建议，且自动降级）；

2. **确定性**：同一输入任何时刻运行，分数与结果完全一致（见 4.4 验证）；

3. **可解释**：每个分数都有分项明细（`score_breakdown`）和原文证据（`evidence` / `evidence_detail`）；

4. **不猜测**：技能未命中绝不判为已掌握，缺失清单严格来自词典提取结果。

## 2. 技能词典与归一化（C1）

### 2.1 数据规模（当前版本）



| 数据项                      | 数量     | 说明                                                      |
| ------------------------ | ------ | ------------------------------------------------------- |
| 技能词（canonical）           | **74** | 覆盖后端 12 / 前端 9 / 数据 11 / ML 25 / DevOps 8 / 大数据 6 / 云 3 |
| 同义词（surface → canonical） | **25** | 缩写、大小写、中英文写法统一映射                                        |
| 子串匹配词                    | 57     | 长词 / 专名 / 中文词，出现即命中                                     |
| 词边界匹配词                   | 17     | 短英文词（Go、Java、SQL、LLM、js 等），防包含误报                        |

### 2.2 两层归一化

**第 1 层&#x20;**`normalize()`：小写 + 去掉空白、连字符、下划线、斜杠、点号及全半角标点。



```
"FastAPI"      → fastapi

"CI/CD"        → cicd

"PyTorch"      → pytorch

"TensorFlow"   → tensorflow

"AI Agent"     → aiagent
```

**第 2 层&#x20;**`to_canonical()`：表面写法 → 规范名（同义词表映射）。



| 表面写法                | 规范名        |
| ------------------- | ---------- |
| `golang` / `GOLANG` | Go         |
| `js`                | JavaScript |
| `cpp`               | C++        |
| `k8s`               | Kubernetes |
| `自然语言处理`            | NLP        |
| `大模型`               | LLM        |
| `AI Agent`          | Agent      |
| `提示词工程`             | Prompt     |
| `python3`           | Python     |

### 2.3 两种匹配模式与防误报原理



* **substring**：规范化后原文包含该词即命中（如 `fastapi`、`机器学习`）；

* **word**（词边界）：只在拉丁字母 / 数字边界处命中，正则形态：



```
r"(?\<!\[a-z0-9]){词}(?!\[a-z0-9])"
```

中文前后天然是边界，不受影响。**这是 C1 防误报的核心**：



| 原文              | 命中         | 不命中  | 原因                   |
| --------------- | ---------- | ---- | -------------------- |
| `使用 MySQL 数据库`  | MySQL      | SQL  | "sql" 前是字母 y，不满足词边界  |
| `使用 GitHub 托管`  | —          | Git  | "git" 后是 h，不满足词边界    |
| `使用 JavaScript` | JavaScript | Java | "java" 后是 s，不满足词边界   |
| `对接 Google API` | —          | Go   | "go" 后是 o，不满足词边界     |
| `使用 Python3 编写` | Python     | —    | `python3` 在同义词表，显式映射 |

## 3. JD 解析与技能分类（C2）

### 3.1 处理流水线



```
JD 原文 → 剥离 YAML 验收标注 → 按句切分 → 技能 span 提取 → 句级信号词分类

&#x20;      → "X 或 Y"并列结构修正 → 多句取最强信号 → 输出必需/加分/否定（带原文证据）
```

### 3.2 切句规则（关键设计）



* **切句符**：`；。！？换行` **与逗号**—— 逗号也切，防止 "熟悉 CI/CD 流程，有 Jenkins 经验者加分" 中的 "加分" 误伤上一段 CI/CD（C2 修过的真实回归 bug）；

* **顿号不切**："了解 Redis 缓存、Kafka 消息队列者加分" 必须整句判定为加分，不能切成两句丢失 "加分" 语义。

### 3.3 信号词表与分类优先级



| 信号类别         | 词数 | 示例                 |
| ------------ | -- | ------------------ |
| 必需（required） | 23 | 熟悉、掌握、熟练、使用、精通、负责… |
| 加分（bonus）    | 7  | 加分、优先、更佳、更好…       |
| 否定（negation） | 9  | 无需、无要求、不要求、不需要…    |

**句内优先级：否定 (4) > 加分 (3) > 必需 (2) > 默认 (1)**，多句出现时取最强信号；没有任何信号词的技能按 "必需・默认" 处理（JD 写出的技能即岗位要求），并显式标注 `signal=必需·默认` 便于审计。

### 3.4 "X 或 Y" 并列结构

同一句内，"或" 字两侧 ±15 个字符内各至少出现一个技能时，判定为**并列可选项，归入加分**：



```
"掌握 MySQL 或 PostgreSQL 等关系型数据库" → MySQL、PostgreSQL 均判为加分
```

### 3.5 典型边界案例



| 输入                            | 结果                      | 说明         |
| ----------------------------- | ----------------------- | ---------- |
| `无需熟悉 Docker 或掌握 Kubernetes`  | Docker、Kubernetes → 否定  | 句级否定词优先    |
| `熟悉 CI/CD 流程，有 Jenkins 经验者加分` | CI/CD → 必需；Jenkins → 加分 | 逗号切句，互不污染  |
| `了解 Redis 缓存、Kafka 消息队列者加分`   | Redis、Kafka → 加分        | 顿号不切句，整体判定 |
| `使用 PYTHON 编写`                | Python → 必需             | 大小写归一化     |

## 4. 评分算法（C3）

### 4.1 公式（冻结契约 v1）



```
总分 = 必需技能覆盖率(60) + 加分技能覆盖率(20) + 经历证据质量(20)
```

**必需技能覆盖率**：`round(60 × 命中必需技能数 / JD 必需技能总数)`；JD 必需为空 → 该项满分 60。

**加分技能覆盖率**：`round(20 × 命中加分技能数 / JD 加分技能总数)`；JD 加分为空 → 该项满分 20。

**经历证据质量（20）**，由三部分组成：



| 子项        | 分值 | 规则                                              | 数据规模                              |
| --------- | -- | ----------------------------------------------- | --------------------------------- |
| 量化成果      | 10 | 命中的量化证据 "片段" 去重计数，每条 2 分，封顶 10                  | 6 条量化正则（数字 + 量词 / 动词 + 数字 / 百分比…） |
| 动作动词      | 5  | 命中的强动词种数，每种 1 分，封顶 5                            | 31 个动作动词（主导 / 负责 / 优化 / 搭建…）      |
| 项目 / 实习证据 | 5  | 命中的经历区块类别数（project/internship/work），每类 2 分，封顶 5 | 3 类区块                             |

总分天然落在 0-100；计算过程完整返回 `score_breakdown`。

### 4.2 建议生成规则（最多 6 条，按优先级）



1. 每个缺失的必需技能 → "简历缺少岗位必需技能「X」，建议…"（附带 JD 原文证据）；

2. 量化分 < 10 → 提醒补充量化成果（"提升 30%"" 处理 10000 条 "）；

3. 动作动词种数 < 3 → 提醒使用强动词；

4. 无任何经历区块 → 提醒补充经历描述。

### 4.3 示例演算（JD = jd\_001 Python 后端开发工程师，必需 6 / 加分 5）



| 简历                    | 必需 (60) | 加分 (20) | 证据 (20) | 总分     | 拆解说明                                                                                          |
| --------------------- | ------- | ------- | ------- | ------ | --------------------------------------------------------------------------------------------- |
| 完整匹配（后端简历）            | 60      | 16      | 19      | **95** | 必需 6/6 满分；加分命中 4/5（Kafka/MySQL/PostgreSQL/Redis）；证据 = 量化 10（≥5 条数字证据封顶）+ 动词 5 + 区块 4（项目 + 工作） |
| 部分匹配（Python/Excel 简历） | 10      | 0       | 9       | **19** | 必需只命中 Python（1/6）；证据 = 量化 2（"转化率提升 15%"）+ 动词 5 + 区块 2（实习）                                     |
| 低匹配（市场运营简历）           | 0       | 0       | 7       | **7**  | 必需 0 命中；证据 = 量化 0 + 动词 5 + 区块 2（工作）；**无虚假匹配技能**                                               |

### 4.4 确定性验证

同一输入连续运行两次分数完全一致（边界用例实测：`81 = 81`；C3 场景 5 同义词用例 `63 = 63`）。原因：纯规则、无随机、无外部 API。

## 6. 已知边界与局限性



1. **词表依赖人工维护**：词表外技能（新框架、新领域词）无法识别；扩展方式为向 `skill_dictionary.json` 与 `synonyms.json` 增补条目（C5 边界用例已固化回归）。

2. **无语义理解**：语义等价但写法不同（如 "会搭网站"≠"Web 前端开发"）不识别，属 P2 范围。

3. **量化分只认数字形态**：不验证数字真实性，也不判断该成果是否关键。

4. **证据质量为形态分**：衡量 "有没有写"，不衡量经历含金量。

5. **罕见句式边界**：同一逗号句内同时出现 "无需 X，掌握 Y" 时，句内否定词会使 Y 也判为否定（MVP 接受，实际 JD 极少见）。

6. **不做黑盒评分**：不接入 LLM 打分（P2），保证分数可解释、可复现、无成本。

7. **免责声明**：匹配分用于辅助判断，不代表录用概率（结果页固定展示）。

## 7. 技术亮点（演示话术）



1. **可解释到证据级**：总分 → 分项 → 技能 → 原文证据，四层可溯源，答辩可直接点开 `/api/matches` 响应逐项讲；

2. **确定性**：同输入同分，评审可当场复现；

3. **零外部依赖**：无 API Key 也能完整演示核心功能；

4. **模块复用**：C1 词典被 C2/C3 共用，同义词 / 词边界一套逻辑贯穿全链路；

5. **一键回归**：`python backend/scripts/validate_boundary.py` 一条命令跑完词典、JD 解析、评分与全部边界用例。
