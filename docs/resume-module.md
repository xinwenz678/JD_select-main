# 简历解析与诊断模块说明（成员 B，任务 B6）

> 适用对象：报告撰写、答辩 PPT 与演示视频的素材来源。
> 代码路径：`backend/app/schemas/resume.py`、`backend/app/services/resume_parser.py`、
> `backend/app/services/resume_diagnose.py`、`backend/app/services/pdf_extractor.py`、`backend/app/api/resumes.py`、
> `frontend/src/pages/ResumeEditorPage.tsx`。
> 接口契约：`docs/resume-contract.md`。样例：`sample_data/`。

## 1. 模块定位

简历模块解决主链路的第一步——**把一段自由文本简历变成结构化、可解释、可编辑的数据**，并给出**不依赖大模型的确定性质量诊断**。

它属于"AI 简历诊断与岗位匹配系统"（T5）中 B 成员的任务包（B1-B6），与 C 的技能词典/评分、A 的记录存储、D 的结果页通过冻结契约衔接：

```text
PDF ──extract──▶ 简历原文 ──parse──▶ 结构化 JSON（基本信息/区块/技能）
简历原文 ──diagnose──▶ 诊断结论（量化亮点/动词建议/结构建议，均带原文行号）
用户（前端 B3）──在结果上人工编辑确认──▶ 交匹配与持久化
```

## 2. 设计原则与边界

| 原则 | 做法 |
|---|---|
| 确定性 | 纯规则引擎，同输入必同输出，便于测试与解释 |
| 不猜 | 识别不到的字段输出 `null` + `warnings`，绝不编造姓名/技能 |
| 可追溯 | 每条诊断带原文行号与所属区块，点击即可定位 |
| 脱敏 | 示例数据全部虚构；接口不记录日志中的完整正文 |
| 可替换 | 技能同义词归一化留给 C 的词典模块，本模块不做重复匹配 |

明确不做（本轮 P1/P2）：扫描件 OCR、docx 上传、大模型 STAR 改写、简历排版美化。

## 3. 解析器（B1/B2）：`resume_parser.py`

### 3.1 区块切分

按行扫描，识别 4 类区块标题（education / experience / projects / skills），标题库含中英文关键词：

- 同一类内关键词按"更长更具体优先"，命中时取**最长匹配**，避免"技能"误吞"专业技能"；
- 标题必须位于清理装饰符号后的**行首**；
- **两字泛词（教育/项目/技能/经历）+ 明显长正文**时不当作标题，防止正文行被误切；
- 支持 `2024.06-2024.09`、`至今`、`Now` 等时间行继续归属当前区块。

输出 `Section{kind, heading, line_start, line_end, lines}`，保留原文行号供诊断定位。

### 3.2 基本信息提取

仅扫描文首 12 行，尽力识别姓名 / 邮箱 / 电话，三字段全部允许缺失：

- 邮箱：标准正则（`xxx@domain.tld`）；
- 电话：`(+86) 1[3-9]xxxxxxxx` 国内手机号；
- 姓名：文首短行且非邮箱/电话/数字的行（支持 `姓名：xxx` 前缀），长度 2-12 取首词。

### 3.3 技能拆分

只从"技能"区块拆词（契约第 2 问确认）：先剥离 `编程语言：` 这类行首标签，再用中文顿号/逗号/分号/竖线/斜杠拆分，过滤括号注释、纯符号、单字符小写噪音，**去重保序**。

### 3.4 Warnings 语义

`warnings` 表示"解析不确定"，与诊断（质量建议）不同：缺教育区块 / 无技能词 / 无姓名各产生一条提示，不阻断流程。

## 4. 诊断器（B4）：`resume_diagnose.py`

对解析结果做**二次原文扫描**，输出三类结论：

| 类别 | 含义 | 示例文案（已实现） |
|---|---|---|
| `quantified` | 经历/项目行命中量化指标，是**正向亮点** | 命中量化指标「12 个」：数据点越具体越可信 |
| `action_verb` | 正文行不以动作动词开头 | 该条经历建议以动作动词开头，突出"我做了什么" |
| `suggestion` | 结构性改进：动词有但缺量化 / 教育无年份 / 技能 < 3 / 缺区块 | 该条有动作但缺少量化结果，说服力可以更强 |

### 4.1 行级判定规则（仅 experience / projects）

1. **只诊断"正文行"**：须以动作动词开头、含量化指标或含成果宾语词（系统/接口/app/pipeline…），三者皆无的行（岗位头衔、项目名、时间开头的条目头、<10 字符标签）自动跳过；
2. 命中「数字 + 单位/百分比」（`12 个`、`30%`、`20 万`、`QPS`…）→ `quantified`；
3. 无动词 → `action_verb`；
4. 动词开头但无量化且行足够长 → `suggestion`（补量化）。

动词库 60+ 中文动词（负责/主导/搭建/开发…）+ 40 英文动词（built/designed/refactored…），允许"独立/协助/高效"等软前缀。

### 4.2 区块级判定

- 教育区块整段无 `19xx/20xx` 年份 → 建议补时间线；
- 缺 education / 缺 experience+projects 区块 → 结构建议；
- 技能词 = 0 或 < 3 → 覆盖偏窄建议。

### 4.3 与 parse 的关系

`diagnose` 内部直接调用 `parse_resume_text`，保证两份输出对同一原文永远一致；诊断结论自带 `line` 行号与 `section`，结果页可高亮原文。

## 5. 接口（B2/B4）

| 接口 | 请求 | 响应要点 |
|---|---|---|
| `POST /api/resumes/parse` | `{"text": "<原文>"}` | `schema_version`、`algorithm_version`、`resume{basic, sections, skills, warnings}` |
| `POST /api/resumes/upload-pdf` | `Content-Type: application/pdf`，请求体为 PDF 二进制 | 提取后的 `text`、`pages` 及完整 parse 结果 |
| `POST /api/resumes/diagnose` | `{"text": "<原文>"}` | `summary{total, quantified, action_verb, suggestion}` + `diagnoses[]` |

- `text` 必填、去除首尾空白后不能为空、> 50000 字符返回 422（前端有对应错误提示）；
- PDF 限 10 MB、30 页，需包含可提取文本；损坏、加密、扫描型或超限文件返回可读错误；
- 两个接口均返回 `algorithm_version: rule-v1`，算法升级不影响字段契约；
- 错误格式遵循 A2 的统一规范，由 A 的中间件兜底。

## 6. 前端编辑确认页（B3）

`frontend/src/pages/ResumeEditorPage.tsx` 实现主流程第 2-3 步（用户流程 2.1 节）：

1. 上传文本型 PDF，或粘贴 / 填充示例简历文本；
2. `parse` 返回后按区块卡片展示，姓名/邮箱/电话与技能标签**可直接编辑**；
3. `diagnose` 结果按区块分组展示，命中行提示可点击定位；
4. 确认后组装 `ParsedResume` 结构交给后续匹配与保存（与 C4/A3 契约对齐）。

## 8. 技术亮点（答辩可讲）

1. **确定性规则替代"看似智能的猜测"**：核心能力全部可单测、可复现，符合课程对"可解释"的要求；
2. **全链路行号溯源**：解析的 `Section.line_start/line_end` 与诊断的 `line` 使用同一套 1 起行号，前端可做"建议 → 原文"的点击定位，而不是只给一段话；
3. **中英文双语言标题 + 防误判**：最长命中 + "泛词后接长正文不算标题"规则，兼顾紧凑英文简历与自由中文排版；
4. **契约先行**：schema 先于实现冻结（`docs/resume-contract.md` 留了 3 个跨成员问题），保证与 C 的词典匹配、A 的持久化字段零冲突。

## 9. 已知局限（写入报告的"展望"）

- 区块标题依赖常见措辞，极特殊排版（无任何标题的纯条目流）识别为 other/缺区块；
- 技能只在"技能"区块内拆分，若全文无技能区块且技能混写在经历中，需要 C 侧做全文兜底扫描（契约问题 2）；
- 年份、数字口径仅做正则识别，不做"矛盾检测"（如结束早于开始）——属于 P1 增强。
